# libScePad technical debt

### Unknown function info

- [scePadUnknown_n3kSX62fgNo](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - imported by PPSA01530 and PPSA13356 and added without an implementation because the titles fail to load without it; its real name is unknown. The two public bodies disagree on its arguments: [sharpemu](https://github.com/sharpemu/sharpemu/blob/85393c2ef87c101294229492595dcc32e9a3c92d/src/SharpEmu.Libs/Pad/PadExports.cs#L90-L100) returns 0 without reading any, while [KytyPS5](https://github.com/KytyPS5/KytyPS5/blob/df5b9b92be7dfd463b47756b707d6d356a9f0550/src/libs/libPad.cpp#L150-L163) reads six and zeroes the fourth argument's count of bytes at the first when they look like a buffer and its size. Raiden IV x MIKADO remix (PPSA08832) calls it once, from a wrapper at 0x15d8a0 that runs `scePadInit` and, when that is not negative, tail-jumps to it without setting up any argument and returns its result, so it takes no arguments there; it returns `PAD_OK` and writes nothing, as sharpemu does. What it does on a console is unknown
- [scePadSetAngularVelocityDeadbandState](../../../core/libs/prx/libScePad/src/PadState.cpp) (libScePad) - with the deadband on, each angular velocity axis whose magnitude is below 0.017453292 rad/s (1 degree per second) reads as 0, before the orientation is integrated; it starts off. Threshold, per-axis test and default follow [duaLib](https://github.com/WujekFoliarz/duaLib/blob/03bad1bea2a36561b520846776f2a07ced6773e0/src/source/duaLib.cpp#L44), which reimplements the PC `libScePad.dll`; the console's threshold is not measured, and the deadband is kept per library rather than per handle since one pad handle exists
- [scePadOpen and scePadOpenExt](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - special ports (type 2) return `DEVICE_NOT_CONNECTED` (0x80920007) because the host has no special controller, and `scePadGetHandle` has no handle for them; whether the console opens a handle and reports the device as disconnected later is unknown. PPSA01317 passes scePadOpenExt a 16-byte param that names the device by vendor and product id (`b7 0e 04 0e ...` for 0x0eb7:0x0e04, the [OpenOrbis](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/7d08613c87e51eba22e530970cdb8e46d7605049/include/orbis/_types/pad.h#L114-L119) `OrbisPadExtParam`) and skips the user on any negative result. scePadOpenExt rejects a null param, then opens the port through scePadOpen and returns the same handle, as [shadPS4](https://github.com/shadps4-emu/shadPS4/blob/cc728e1c7c97bb9dca71dea78e9e26a87a220280/src/core/libraries/pad/pad.cpp#L352-L356) and [fpPS4](https://github.com/red-prig/fpPS4/blob/accf9ec255e6d102aef5c1a9cf04a8059cb769b9/src/ps4_libscepad.pas#L373-L376) do for PS4; the vendor and product id in the param are not checked against the host controller
- [scePadReadExt](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the `(int handle, ScePadData* data, int count)` signature comes from [OpenOrbis](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/a2f0d7f282d672e205caaaa648dee0b5dfcde908/include/orbis/Pad.h#L75) and the [GoldHEN gamepad_helper](https://github.com/GoldHEN/GoldHEN_Plugins_Repository/blob/92fbac926f5351bbd0f5fbcf57c44053fc90ccf6/plugin_src/gamepad_helper/include/pad.h#L170) header. PS4 plugins that hook scePadRead call it to fetch the real samples of a standard pad ([example](https://github.com/pozpo/ps4-xbox-series-plugin/blob/14d669fdf408c75cae168b1a2ba8eb2355129a0a/src/hooks.c#L326)), so it reads through scePadRead: the same handle check, argument errors and sample queue. Whether the console's Ext read adds anything for special controllers is unknown, since none opens here
- [scePadOutputReport](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the `(int handle, int type, uint8_t* report, int length)` signature comes from [OpenOrbis](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/a2f0d7f282d672e205caaaa648dee0b5dfcde908/include/orbis/Pad.h#L35), [fpPS4](https://github.com/red-prig/fpPS4/blob/accf9ec255e6d102aef5c1a9cf04a8059cb769b9/src/ps4_libscepad.pas#L388) and [OrbisInstrumentalizer](https://github.com/InvoxiPlayGames/OrbisInstrumentalizer/blob/94ec5b0443251ed33c1a5e923bd19d702ae20bc2/source/pad_hooks_ghl.c#L115-L127), whose Guitar Hero Live hook sends the reports to a handle it took from scePadOpenExt on a special port. Special ports never open here and the standard pad is driven through SDL, which has no raw report channel, so a valid handle with a report returns `NOT_PERMITTED` (0x80920101), the error [duaLib](https://github.com/WujekFoliarz/duaLib/blob/03bad1bea2a36561b520846776f2a07ced6773e0/src/source/duaLib.cpp#L774) returns for an operation the controller type does not support. An invalid handle returns `PAD_ERROR_INVALID_HANDLE` and a null report `PAD_ERROR_INVALID_ARG`; the report type and length are not checked, and nothing reaches the controller. What the console returns for a DualSense handle is not measured
- [scePadVrControllerReadState](../../../core/libs/prx/libScePad/Export.cpp) (libScePad, NID `iA-DdobUen8`) - the name hashes to the imported NID; the `(int handle, void* state)` signature follows [PS5VR](https://github.com/theghostonline/PS5VR/blob/0e408909ce7a39891a2e06eee3438d07a09e11e3/app/src/app_vr.c#L326-L369) (PPSA99177), which passes a PS VR2 Sense controller handle from `scePadOpen` type 3 or 4 and a 0x68-byte state it reads as buttons at 0, stick bytes at 4 and a connected byte at 0x40. The title calls it only after `sceHmd2Initialize` succeeds, which it does not here. No Sense controller handle can exist, since scePadOpen refuses port types 3 and 4 and the only handle is the standard pad: an unknown handle returns `PAD_ERROR_INVALID_HANDLE`, a null state `PAD_ERROR_INVALID_ARG`, and the standard handle `NOT_PERMITTED` (0x80920101), the same answer as scePadOutputReport for an operation the controller does not support. The state is never written and its layout is otherwise unknown; what the console returns for a handle that is not a Sense controller is not measured
- [scePadVrControllerRead, scePadVrControllerGetTriggerEffectState, scePadVrControllerSetTriggerEffect, scePadVrControllerSetVibration and scePadVrControllerSetVibrationMode](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - no source shows their parameters. Each signature is inferred from the standard call of the same name (`scePadRead`, `scePadGetTriggerEffectState`, `scePadSetTriggerEffect`, `scePadSetVibration`, `scePadSetVibrationMode`) and from `(int handle, void* state)` of scePadVrControllerReadState: a handle, then a pointer, a pointer and count for Read, or a mode for SetVibrationMode. They answer like scePadVrControllerReadState, checking only the handle, a null pointer and a count below 1; nothing is read through the pointers, nothing is written, the vibration mode is not checked, and the standard pad's vibration and trigger state stay unchanged
- [scePadSetVibrationMode](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - modes 1 to 3 and 5 are accepted and stored. On a PS5 (firmware 13.60) the call returns `0x80920005` before `scePadInit`, then rejects a mode of 0 or below with `INVALID_ARG` before it checks the handle, and returns `INVALID_HANDLE` for a bad handle with any higher mode; whether an open handle accepts modes above 3 was not measured, since the payload could not open a pad; 5 is accepted because PPSA25286 passes it on its open handle at start-up; the meanings of modes 3 and 5 are unknown (PPSA21480 calls it with 3 right after `scePadOpen` and aborts on failure; [SharpProspero](https://github.com/SvenGDK/SharpProspero/blob/main/src/SharpProspero/Interop/Pad/Pad.cs) names only 1 and 2). The stored mode has no other effect
- [scePadIsRemoteController](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the name hashes to NID `fCWdlnmB1Ks`; the signature `(int handle, bool* remote)` comes from PPSA16064, which zeroes a byte, passes its address after `scePadGetControllerInformation` and ignores the result. The error codes follow the other pad calls. Controllers are local devices, so the answer is always false
- [scePadSetAngularVelocityBiasCorrectionState](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - inferred signature `(int handle, bool enabled)` follows `scePadSetTiltCorrectionState` and `scePadSetAngularVelocityDeadbandState`; an invalid handle returns `PAD_ERROR_INVALID_HANDLE`, and the state controls the gyro bias integrator used by motion fusion
- [scePadUnknown_zBsgF0q8DIM](../../../core/libs/prx/libScePad/Export.cpp) (libScePad, NID `zBsgF0q8DIM`) - PPSA03671 imports it and fails to load without it. The aerolib list has no name for the NID, and none of the pad names in SharpProspero, shadPS4 or OpenOrbis, nor the trigger effect, motion sensor, VR controller, HD and haptic names tried, hashes to it. It is declared without parameters and throws. The title's executable has an import stub for it but no call, jump or address reference to that stub, so the argument count and whether the result is used are unknown
