# libScePad technical debt

### Silent stubs

- [scePadEnableExtensionPort](../../../core/libs/prx/libScePad/Export.cpp) returns success without changing extension-port state. The boolean argument is recovered; connected-device behavior is not modeled.

### Unknown function info

- [libScePad profile and device-setting exports](../../../core/libs/prx/libScePad/Export.cpp) - profile getters, tuning, saved settings, USB state, shared output and virtual-device setting arguments are recovered. Hunt and Leonardo reset each consume only a handle; physical VR USB status consumes only an output pointer. Remote settings output is 64 bytes and license-controller information is 1224 bytes. Kernel ioctl payload fields remain incomplete.

- [libScePad report and tracking exports](../../../core/libs/prx/libScePad/Export.cpp) - read, extended-read, tracker, UI, VR-controller and report argument registers are recovered. Feature reports use a byte report ID and 64-bit byte count, capped at 64. VR trigger effects consume a 56-byte record; the dual-controller call uses two handles and a mask with records at offsets 8 and 64. Remaining payload field layouts use incomplete declarations, including extended samples and kernel-owned extension reports.

- [scePadUnknown_n3kSX62fgNo](../../../core/libs/prx/libScePad/Export.cpp) (libScePad, NID `n3kSX62fgNo`) - the name is unknown, and the 0 returned after `scePadInit` is inferred, not measured. In the OS 10.01 system module the function takes no arguments, returns `0x80920005` before `scePadInit`, and otherwise sends a per-process value of 1 to ShellCore over Mbus, returning `0x809200ff` if that call fails and 0 if it succeeds, with or without an open handle. The #3177 probe measured `0x809200ff` in a process that is not a game; a game process is assumed to get 0. The ShellCore setting it changes is unknown and not modelled. Raiden IV x MIKADO remix (PPSA08832) calls it once, from a wrapper at 0x15d8a0 that runs `scePadInit` and, when that is not negative, tail-jumps to it without setting up any argument
- [scePadSetAngularVelocityDeadbandState](../../../core/libs/prx/libScePad/src/PadState.cpp) (libScePad) - with the deadband on, each angular velocity axis whose magnitude is below 0.017453292 rad/s (1 degree per second) reads as 0, before the orientation is integrated; it starts off. Threshold, per-axis test and default follow [duaLib](https://github.com/WujekFoliarz/duaLib/blob/03bad1bea2a36561b520846776f2a07ced6773e0/src/source/duaLib.cpp#L44), which reimplements the PC `libScePad.dll`; the console's threshold is not measured, and the deadband is kept per library rather than per handle since one pad handle exists
- [scePadOpen and scePadOpenExt](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the special port (type 2) opens a handle per user (`PAD_SPECIAL_HANDLE` + slot, 16 slots for the console's 16 accounts, a 17th user gets the unknown-user code 0x809b0081) that every pad call accepts: reads give the rest record (sticks 0x80, orientation w 1, acceleration y 1, `connected` false), information is zeroed, extended information has device class -1, setters succeed without effect. Not measured: the console's own handle values (fresh per open), a PS5, and the calls the PS4 Pro survey (firmware 10.71, no special controller) did not cover; it measured open, `ALREADY_OPENED`, `scePadGetHandle`, both reads, both informations, the five setters above, close, and that two logged-in users get independent handles. `scePadOpenExt` returns `DEVICE_NOT_CONNECTED` (0x80920007) for special ports, unmeasured; PPSA01317 skips a user on any negative result. A standard port, and the remote port of the system user, open through `scePadOpen` and get the standard handle
- [scePadReadExt](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the `(int handle, ScePadData* data, int count)` signature comes from [OpenOrbis](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/a2f0d7f282d672e205caaaa648dee0b5dfcde908/include/orbis/Pad.h#L75) and the [GoldHEN gamepad_helper](https://github.com/GoldHEN/GoldHEN_Plugins_Repository/blob/92fbac926f5351bbd0f5fbcf57c44053fc90ccf6/plugin_src/gamepad_helper/include/pad.h#L170) header. PS4 plugins that hook scePadRead call it to fetch the real samples of a standard pad ([example](https://github.com/pozpo/ps4-xbox-series-plugin/blob/14d669fdf408c75cae168b1a2ba8eb2355129a0a/src/hooks.c#L326)), so it reads through scePadRead: the same handle check, argument errors and sample queue. Whether the console's Ext read adds anything for special controllers is unknown, since none opens here. The native signature passes an extended data record, whose layout is not recovered; only a `ScePadData` is written to it
- [scePadOutputReport](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the native `(handle, uint8_t report id, const void* data, uint64_t size)` registers match the PS4 `(int handle, int type, uint8_t* report, int length)` signature of [OpenOrbis](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/a2f0d7f282d672e205caaaa648dee0b5dfcde908/include/orbis/Pad.h#L35), [fpPS4](https://github.com/red-prig/fpPS4/blob/accf9ec255e6d102aef5c1a9cf04a8059cb769b9/src/ps4_libscepad.pas#L388) and [OrbisInstrumentalizer](https://github.com/InvoxiPlayGames/OrbisInstrumentalizer/blob/94ec5b0443251ed33c1a5e923bd19d702ae20bc2/source/pad_hooks_ghl.c#L115-L127), whose Guitar Hero Live hook sends the reports to a handle it took from scePadOpenExt on a special port. Special ports never open here and the standard pad is driven through SDL, which has no raw report channel, so a valid handle with a report returns `NOT_PERMITTED` (0x80920101), the error [duaLib](https://github.com/WujekFoliarz/duaLib/blob/03bad1bea2a36561b520846776f2a07ced6773e0/src/source/duaLib.cpp#L774) returns for an operation the controller type does not support. An invalid handle returns `PAD_ERROR_INVALID_HANDLE` and a null report `PAD_ERROR_INVALID_ARG`; the report id and size are not checked, and nothing reaches the controller. What the console returns for a DualSense handle is not measured
- [scePadVrControllerReadState](../../../core/libs/prx/libScePad/Export.cpp) (libScePad, NID `iA-DdobUen8`) - the name hashes to the imported NID; the `(int handle, void* state)` signature follows [PS5VR](https://github.com/theghostonline/PS5VR/blob/0e408909ce7a39891a2e06eee3438d07a09e11e3/app/src/app_vr.c#L326-L369) (PPSA99177), which passes a PS VR2 Sense controller handle from `scePadOpen` type 3 or 4 and a 0x68-byte state it reads as buttons at 0, stick bytes at 4 and a connected byte at 0x40. The title calls it only after `sceHmd2Initialize` succeeds, which it does not here. No Sense controller handle can exist, since scePadOpen refuses port types 3 and 4 and only the standard pad handle is accepted (a special-port handle is unknown here): an unknown handle returns `PAD_ERROR_INVALID_HANDLE`, a null state `PAD_ERROR_INVALID_ARG`, and the standard handle `NOT_PERMITTED` (0x80920101), the same answer as scePadOutputReport for an operation the controller does not support. The state is never written; what the console returns for a handle that is not a Sense controller is not measured
- [scePadVrControllerReadState](../../../core/libs/prx/libScePad/Export.cpp) - the 104-byte output layout is recovered, including buttons, stick, triggers, touch fields, motion, connection state and timestamp. Touch-value semantics and kernel report production remain incomplete; the export still throws.
- [scePadVrControllerRead, scePadVrControllerGetTriggerEffectState, scePadVrControllerSetTriggerEffect, scePadVrControllerSetVibration and scePadVrControllerSetVibrationMode](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the signatures are the recovered native ones: Read takes a handle, an array of 104-byte samples and a count, GetTriggerEffectState the left and right handles and a state output, SetTriggerEffect a handle and an effect, SetVibration a handle and an 8-bit intensity, and SetVibrationMode a handle and a mode. They answer like scePadVrControllerReadState, checking only the (left) handle, a null pointer and a count below 1; nothing is read through the pointers, nothing is written, the intensity and vibration mode are not checked, and the standard pad's vibration and trigger state stay unchanged
- [scePadVrControllerReadCombinedState](../../../core/libs/prx/libScePad/Export.cpp) - the two handle arguments and 128-byte output are recovered; output field semantics remain incomplete.
- [scePadSetVibrationMode](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - modes 1 to 3 and 5 are accepted and stored. On a PS5 (firmware 13.60) the call returns `0x80920005` before `scePadInit`, then rejects a mode of 0 or below with `INVALID_ARG` before it checks the handle, and returns `INVALID_HANDLE` for a bad handle with any higher mode; whether an open handle accepts modes above 3 was not measured, since the payload could not open a pad; 5 is accepted because PPSA25286 passes it on its open handle at start-up; the meanings of modes 3 and 5 are unknown (PPSA21480 calls it with 3 right after `scePadOpen` and aborts on failure; [SharpProspero](https://github.com/SvenGDK/SharpProspero/blob/main/src/SharpProspero/Interop/Pad/Pad.cs) names only 1 and 2). The stored mode has no other effect
- [scePadIsRemoteController](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the name hashes to NID `fCWdlnmB1Ks`; the signature `(int handle, bool* remote)` comes from PPSA16064, which zeroes a byte, passes its address after `scePadGetControllerInformation` and ignores the result. The error codes follow the other pad calls. Controllers are local devices, so the answer is always false
- [scePadIsDS4Connected, scePadIsBlasterConnected and scePadIsMoveConnected](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the `bool (int handle)` signatures are recovered; the library reports one DualSense to every title (see Touchpad resolution below), so no DualShock 4, Blaster or Move controller is ever behind a handle and each call answers false for any handle. The console's answer for an invalid handle is not measured
- [scePadSetAngularVelocityBiasCorrectionState](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - inferred signature `(int handle, bool enabled)` follows `scePadSetTiltCorrectionState` and `scePadSetAngularVelocityDeadbandState`; an invalid handle returns `PAD_ERROR_INVALID_HANDLE`, and the state controls the gyro bias integrator used by motion fusion
- [scePadGetAccessibilityControllerState](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the value a console reports for a DualSense is not measured; the emulated pad, which is not an Access controller, reports 0. ### Functional

- [Touchpad resolution](../../../core/libs/prx/libScePad/include/PadState.hpp) (libScePad) - the library reports a DualSense to every title, so the controller information reports its touchpad, 1920 by 1080 at 44.86 pixels per cm, and the host controller's fingers and the keyboard touch contacts are placed in that range. [duaLib](https://github.com/WujekFoliarz/duaLib/blob/0b39f92261e2ff0e77eb0dac00943be6970e0dbf/src/source/duaLib.cpp#L847-L849) reports these values for a DualSense and 1920 by 943 at 44 for a DualShock 4, and the Linux kernel's [hid-playstation](https://github.com/torvalds/linux/blob/cd4f494ba535e848e2d299707d363de84e61a518/drivers/hid/hid-playstation.c#L177-L178) holds 1920 by 1080 against 1920 by 942 for the DualShock 4. A DualShock 4 on the host reports through the DualSense range too, so its last touchpad rows are never reached. A PS5 on firmware 13.40 reported 1920 by 1080 at 44.86 and stick dead zones of 13 to a retail title
- [scePadDisableTriggerEffect](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the boolean is stored per pad; disabling turns both trigger effect blocks off in the next output report and enabling restores the last requested effects. The console's exact behavior, its return codes and whether it also affects effects requested by another process are unmeasured
- [scePadSetTriggerEffectStrength, scePadGetTriggerEffectInternalState and scePadSetTriggerEffectExt](../../../core/libs/prx/libScePad/Export.cpp) (libScePad) - the strength argument's units and range, the `PadTriggerInternalState` layout and the `PadTriggerEffectExtended` layout are unknown, so all three still throw. The DualSense output report has an unexposed trigger motor power reduction field and `scePadSetTriggerEffectStrength` may map to it, but that is not measured
