# libSceVrTracker2 technical debt

### Silent stubs

- [libSceVrTracker2](../../../core/libs/prx/libSceVrTracker2/Export.cpp) tracks only its own initialization. No PS VR2 device can be opened on the host (`sceHmd2Open` never returns a handle and `scePadOpen` rejects the VR controller port types), so `sceVrTracker2RegisterDevice` rejects every handle with `INVALID_DEVICE_HANDLE`, `sceVrTracker2UnregisterDevice` rejects every handle with `ARGUMENT_INVALID`, as PS4's `sceVrTrackerUnregisterDevice` does for a handle it does not know ([shadPS4](https://github.com/shadps4-emu/shadPS4/blob/main/src/core/libraries/vr_tracker/vr_tracker.cpp)), and once initialized `sceVrTracker2GetResult`, `sceVrTracker2ResetLocalCoordinate`, `sceVrTracker2LocateCoordinateSystem` and `sceVrTracker2GetPlayAreaOrientedBoundingBox` return `DEVICE_NOT_REGISTERED` and write nothing. `sceVrTracker2Initialize` keeps neither the work memory nor the thread settings and starts no tracker thread, and does not hold the work memory to the 32 MiB `sceVrTracker2QueryMemory` reports, since the console's error for a smaller one is unknown. Its success is not the console's: with PPSA05666's parameter and no headset the console's initialization did not return within a minute (below). After initialization `sceVrTracker2GetCoordinateSystem`, `sceVrTracker2GetPlayAreaBoundaryGeometry`, `sceVrTracker2SetCoordinateSystem` and the unnamed exports that answer 0x8A740001 or clear a result before it throw, because what an initialized tracker answers there is unknown. PPSA01317 only reaches this library after `sceHmd2Initialize` succeeds, which it does not here
- [libSceVrTracker2](../../../core/libs/prx/libSceVrTracker2/Export.cpp) answers before initialization as the console's module does, measured in #7463 on a retail PS5 (firmware 13.60) with no PS VR2 headset by calling each of the 115 NIDs with null arguments, zeroed buffers and buffers filled with 0xAA and 0x01: 99 return 0x8A740001 and write nothing; `XknY0IDcOwU` and `ark13GkiskA` return 0x8A740006 for a null first argument and otherwise clear its first 24 and 16 bytes and return 0x8A740001; `-YvjOUph8B0` returns 0x8A740006 for a null second argument and otherwise 0x8A740001; `QyZvFyf-QEk` and `fTYZOZepkqE` return 0 and write nothing; `TZIUIk9id3c` writes 0xC000, 0, 0x40 and 0x40 as `uint32`, `uint32`, `uint16` and `uint16` at offsets 4 to 15 of its first argument and returns 0; `IB0qcDVu8vU` clears the `uint32` at its first argument and returns 0. The last two crash on the console for a null first argument and throw here. The 99 include the named exports, which check initialization first here as well. Named export signatures and play-area output layouts are recovered; the unnamed exports carry this library's own names, with their recovered signatures below

### Unknown function info

- [libSceVrTracker2](../../../core/libs/prx/libSceVrTracker2/Export.cpp) signatures and parameter layouts follow [PS5VR](https://github.com/theghostonline/PS5VR/blob/0e408909ce7a39891a2e06eee3438d07a09e11e3/app/src/app_vr.c#L58-L64) (PPSA99177), which drives PS VR2 on FW 13.60: `sceVrTracker2QueryMemory(param, result)` with a 0x20-byte param (size at `+0`, profile at `+4`, 0 being "the only one open to apps") and the [memory size and alignment](https://github.com/theghostonline/PS5VR/blob/0e408909ce7a39891a2e06eee3438d07a09e11e3/app/src/app_vr.c#L620-L641) as the second and third words of the result; `sceVrTracker2Initialize(param)` with a 0x48-byte param (size at `+0`, work memory at `+0x20`, its size at `+0x28` and alignment at `+0x2c`; PS5VR also sets 700 at `+8` and `+0xc` and 0x1f00 at `+0x10` and `+0x18`, unchecked here); `sceVrTracker2RegisterDevice(type, handle)`, type 0 for the headset and 1 and 2 for the controllers; `sceVrTracker2GetResult(param, result)` with a [0x20-byte param](https://github.com/theghostonline/PS5VR/blob/0e408909ce7a39891a2e06eee3438d07a09e11e3/app/src/app_vr.c#L669-L677) (size at `+0`, handle at `+4`, time at `+0x10`), accepted here next to the recovered 0x30-byte form; `sceVrTracker2UnregisterDevice(handle)`; and `sceVrTracker2Finalize()`. Size fields must match exactly, as PS4's libSceVrTracker requires; the device types, profiles and memory alignments the console accepts are unknown. `sceVrTracker2ResetLocalCoordinate`, `sceVrTracker2LocateCoordinateSystem`, `sceVrTracker2GetPlayAreaOrientedBoundingBox`, `sceVrTracker2GetCoordinateSystem`, `sceVrTracker2GetPlayAreaBoundaryGeometry` and `sceVrTracker2SetCoordinateSystem` read none of their recovered parameters, so arguments the console might reject first are not checked
- [libSceVrTracker2](../../../core/libs/prx/libSceVrTracker2/Export.cpp) - initialization (`6Jy73SRfG-o`) takes one parameter of 0x48 bytes. PPSA05666 passes the size 0x48 at offset 0, `uint32` 0x100 and 0x2BC at 0x8 and 0xC, `uint64` 0x1FFF at 0x10 and 0x18, a pointer to its work memory at 0x20, and the memory query's 32 MiB and 64 KiB as `uint32` at 0x28 and 0x2C, with the other bytes zero; the priority and CPU mask meanings of 0x8 to 0x1F are assumed from the values. Called with that parameter and 32 MiB of anonymous memory from a homebrew payload on a PS5 (firmware 13.60) with no PS VR2 headset, it did not return within a minute, so what it returns without a headset is unknown. The layout matches PS5VR's, which `sceVrTracker2Initialize` checks as above
- [sceVrTracker2Initialize](../../../core/libs/prx/libSceVrTracker2/Export.cpp) - the 72-byte parameter layout is recovered, including thread priorities, CPU affinity masks, work memory, size/alignment and coordinate system. Meanings of the 32-bit option at 0x30 and byte options at 0x38/0x39 remain unresolved; initialization keeps none of these settings (above).
- [libSceVrTracker2](../../../core/libs/prx/libSceVrTracker2/Export.cpp) error codes put PS4 libSceVrTracker's low byte ([shadPS4](https://github.com/shadps4-emu/shadPS4/blob/main/src/core/libraries/vr_tracker/vr_tracker_error.h), 0x812608xx) under 0x8A740000: `NOT_INIT` 0x8A740001, `ALREADY_INITIALIZED` 0x8A740002, `DEVICE_NOT_REGISTERED` 0x8A740003, `ARGUMENT_INVALID` 0x8A740006 and `INVALID_DEVICE_HANDLE` 0x8A740007. 0x8A740001 and 0x8A740006 are observed on a console (above); the others are not. [PS5VR](https://github.com/theghostonline/PS5VR/blob/0e408909ce7a39891a2e06eee3438d07a09e11e3/app/src/vr_system.c#L126-L132) replaces a libSceVrTracker2 export with one of "the same contract" that returns it for bad arguments. Its 0x8A740009 for a buffer that is too small does not match PS4's 0x09 (`INTERNAL_ERROR`), so the mapping is unverified. Initialization is checked first, as on PS4, except in `sceVrTracker2Initialize`, which checks for a previous initialization first, and `sceVrTracker2QueryMemory`, which needs none
- [libSceVrTracker2](../../../core/libs/prx/libSceVrTracker2/Export.cpp) - seven unnamed exports throw. `9R6W33Au4B4`, like initialization (`6Jy73SRfG-o`), returns 0x8A740006 on the console for null arguments, for zeroed, 0xAA- and 0x01-filled buffers and for a size field from 8 to 0x400 in any of the first three arguments; initialization also returned it for the memory query's parameter with 32 MiB aligned to 64 KiB passed inside the parameter or as further arguments, so the parameter layout it accepts is unknown. `NBhWy+Gl0tY` returns 0x8A740006 for those buffers but crashes for null arguments; `jRmuXjsknsI` returns 0x8A740006 for null arguments and crashes for buffers, also when every 8-byte slot points at readable memory; `O8ZkTFtvUL4`, `940WPg+WwIk`, `oZDm1bynCaA` and `U1VYczwqukY` crash for both
- [libSceVrTracker2](../../../core/libs/prx/libSceVrTracker2/Export.cpp) - the seven anonymous throwing exports now have their consumed argument slots restored. Calibration output (`jRmuXjsknsI`) uses a 32-bit capacity with 608/1216-byte variants; its fields remain unresolved. Mesh requirements (`NBhWy+Gl0tY`) contain four 32-bit counts/sizes. The mode/buffer/capacity/size export (`9R6W33Au4B4`) uses 64-bit sizes. The 32/48-byte result parameters are recovered; result output and pose parameters still need full layouts; the telemetry input (`oZDm1bynCaA`) spans 7024 bytes. Their bodies remain unimplemented.

- [Anonymous tracking queries](../../../core/libs/prx/libSceVrTracker2/Export.cpp) still lack initialized behavior. The paired option setter/getter consume 28/40-byte records with three integer options, a reset byte and one/two float vectors; option meanings remain unresolved. The scalar query uses an 8-byte size/float record. Diagnostic output spans 4096 bytes, extended output 0xD02E8 bytes, and tracking configuration input 1024 bytes; their fields remain unresolved. The relative-pose query uses two coordinate-system selectors and a 64-byte output containing a pose and 32 cleared bytes; the counter query uses a 64-bit output and a 32-bit selector whose meaning remains unresolved. Remaining aliases still need individual signatures.

- [Anonymous diagnostic exports](../../../core/libs/prx/libSceVrTracker2/Export.cpp) have separate pointer contracts for composite poses, configuration, camera images, sensor frames, tracking status and boundary parameters. The camera-image query takes a 32-bit byte count and an in/out frame identifier; diagnostics use six 512-byte text sections, and the mode setter uses a 12-byte size/mode/float record. Composite pose, sensor/status, configuration and boundary fields still require reconstruction; none of these exports supports initialized operation.

- [Camera-frame exports](../../../core/libs/prx/libSceVrTracker2/Export.cpp) do not acquire or release native buffers. Their descriptor has a selector, two identifiers, dimensions, pitch, pixel pointer and buffer index; native acquisition writes the first 36 bytes, leaving natural tail padding untouched. The optional 48-byte metadata record and identifier meanings remain unresolved. The scalar-option setter/getter use a float value/output, but its units and meaning remain unresolved.

- [Device and spatial queries](../../../core/libs/prx/libSceVrTracker2/Export.cpp) retain uninitialized responses. Position queries use a three-float input or a device handle and a 36-byte size/status/two-vector/scalar result; the vector and scalar meanings remain unresolved. The bounds query uses the recovered 80-byte oriented box. Device-boundary operations consume a handle and selector; their internal parameter layout differs from the public boundary record and remains unresolved, as do the 28-byte device-calibration status and reset-pose input.

- [Map and flag queries](../../../core/libs/prx/libSceVrTracker2/Export.cpp) retain uninitialized responses. Map initialization takes a device handle and a pointer to one float; map data retrieval takes an output and a 32-bit size constrained to 2048. Map data and status field meanings remain unresolved. Tracking flags use a required boolean output and an optional byte output, rather than an argument-free alias.

- [Diagnostic records](../../../core/libs/prx/libSceVrTracker2/Export.cpp) have individual output-pointer signatures, but field interpretation remains incomplete. Native runtime status clears 88 bytes; diagnostic state writes 120 bytes, sensor diagnostics reach byte 339, device diagnostics reach byte 6983, timing diagnostics write 80 bytes, and sensor summary writes 32 bytes. The map-configuration getter/setter exchange the same 72-byte record. These exports still return only the uninitialized error.

- [Extended result and boundary fitting](../../../core/libs/prx/libSceVrTracker2/Export.cpp) retain uninitialized responses. The extended result spans 816 bytes; its coordinate-specific parameter prefixes the 48-byte query with a coordinate selector and four-byte padding. Boundary fitting takes the recovered point list, optionally returns two 80-byte bounds, and writes four byte flags plus four floats; flag and dimension semantics remain unresolved. The device-center output is a 16-byte size/three-float record.

- [Mesh and image-pose utilities](../../../core/libs/prx/libSceVrTracker2/Export.cpp) retain uninitialized responses. Mesh generation takes vertex and 16-bit index outputs plus a 32-bit format. Timed-pose queries take an in/out result, timestamp and user tag. Image submission consumes a record with format at byte 16 and a data pointer at byte 80; image-pose retrieval uses an in/out record with a buffer pointer and capacity. Record fields and initialized algorithms remain incomplete. Scalar queries use float outputs; the map-scalar query also consumes map data.

- [Legacy unsupported operations](../../../core/libs/prx/libSceVrTracker2/Export.cpp) have separate input-pointer signatures. Two consume only the size prefix of 12/20-byte records, leaving their other fields unrecoverable from these bodies. The coordinate operation reads a selector at byte 4 but always returns unsupported after initialization; the remaining record layout is unresolved.
