# libSceLibreSsl technical debt

### Unknown function info

- [libSceLibreSsl pending exports](../../../core/libs/prx/libSceLibreSsl/Export.cpp) - the named callable exports still declared there are listed in the [PS5 3.20 export table](https://github.com/DNNDHH/PS5-3.20_Libs/blob/b2a77c09cd71c01f34c790cfbe98c751a13262ad/libSceLibreSsl.c) and were cross-checked against the same module in PS5 firmware 13.60. Their signatures and behaviour are unverified; the declarations use the no-parameter unknown-signature convention and throw through `NotImplemented_nid_no_patch`.
- [MD4, MD5, SHA1, SHA224, SHA256, SHA384 and SHA512 Init/Update/Final and SHA256](../../../core/libs/prx/libSceLibreSsl/src/Digest.cpp) (libSceLibreSsl) - signatures and context layouts follow the [LibreSSL headers](https://github.com/libressl/openbsd/blob/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/sha/sha.h), and buffering and `Final` follow its [sources](https://github.com/libressl/openbsd/tree/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/sha); the module's LibreSSL version is unknown and nothing is checked on the console. Behaviour that differs between LibreSSL versions throws: `SHA256` with a null digest buffer (older versions return a static buffer) and `SHA512_Final` with the SHA-512/224 or SHA-512/256 digest length. Null contexts, null input with a nonzero length, null digest buffers in the 32-bit `Final` functions and a buffered byte count that is not below the block size, which LibreSSL does not check, throw
- [AES_set_encrypt_key, AES_set_decrypt_key, AES_encrypt, AES_decrypt, AES_ecb_encrypt, AES_cbc_encrypt, AES_cfb128_encrypt, AES_ctr128_encrypt](../../../core/libs/prx/libSceLibreSsl/src/Aes.cpp) (libSceLibreSsl) - follow LibreSSL's [aes.h](https://github.com/libressl/openbsd/blob/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/aes/aes.h) and [mode code](https://github.com/libressl/openbsd/tree/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/modes); the console's LibreSSL version and build are unknown. The `AES_KEY` schedule uses the generic C layout (big-endian words, `rounds` 10, 12 or 14); the console's assembly or AES-NI code may store another, so a schedule the title reads or fills is unverified. A failed key setup zeroes the key as current LibreSSL does (older versions leave it unchanged), and CTR leaves the last keystream block in `ecount_buf` even at a block boundary. Null pointers, other `rounds` values and a CFB or CTR position outside 0-15 throw
- [RAND_add, RAND_bytes, RAND_status, RAND_load_file, RAND_file_name, CRYPTO_malloc, CRYPTO_free, CRYPTO_set_mem_functions](../../../core/libs/prx/libSceLibreSsl/src/Runtime.cpp) (libSceLibreSsl) - follow LibreSSL's [rand_lib.c, randfile.c](https://github.com/libressl/openbsd/tree/0f0b16dc977f6ca499f0f4540078d992c96da597/src/lib/libcrypto/rand) and [malloc-wrapper.c](https://github.com/libressl/openbsd/blob/0f0b16dc977f6ca499f0f4540078d992c96da597/src/lib/libcrypto/malloc-wrapper.c), which are the same in 2.6.5 (3.4.3 linked); nothing is checked on the console. `RAND_bytes` reads host entropy and `CRYPTO_malloc` and `CRYPTO_free` use the guest heap. `CRYPTO_malloc` throws for a size of zero or less, which returns null up to 3.4 and calls `malloc` with a `size_t` size in later versions. A null buffer with a positive length throws
- [DES_set_key, DES_ecb_encrypt, DES_set_odd_parity](../../../core/libs/prx/libSceLibreSsl/Export.cpp) (libSceLibreSsl) - the 128-byte `DES_key_schedule` holds the 8-byte key followed by zeros instead of LibreSSL's precomputed subkeys, so a title reading its contents sees different bytes; `DES_ecb_encrypt` derives the subkeys through mbedtls on each call. Not compared with the console. Results follow LibreSSL [des_key.c](https://github.com/libressl/openbsd/blob/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/des/des_key.c) and [des.c](https://github.com/libressl/openbsd/blob/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/des/des.c): `DES_set_key` skips the parity and weak-key checks and returns 0, as it does while `DES_check_key` is 0 (that variable is not in the PS5 export inventory), a nonzero `enc` encrypts, and `DES_set_odd_parity` sets each byte's low bit for odd parity. Null pointers throw where LibreSSL faults

### LibreSSL version and structure layouts

- [EVP, ERR, BIO, BN, X509, UI and library exports](../../../core/libs/prx/libSceLibreSsl/src) - the console's LibreSSL version is unknown. The export list has the OpenSSL 1.0 style calls (`HMAC_CTX_init`, `EVP_MD_CTX_create`, `EVP_CIPHER_CTX_init`, `sk_num`) and none of the `HMAC_CTX_new` family that LibreSSL added in 2.7.0, so the prototypes and the layouts of the structures a title allocates or reads follow the [LibreSSL 2.6.3 headers](https://github.com/openbsd/src/tree/70f155023853bdbfcd08e322323f5bfc8a542d3d/lib/libcrypto) (OpenBSD 6.2) for LP64 and the behaviour the manual pages of that tree or, where those are missing, the current [LibreSSL manual pages](https://github.com/openbsd/src/tree/master/lib/libcrypto/man). The sizes are checked with `static_assert` (`EVP_MD_CTX` 48 bytes, `HMAC_CTX` 288, `EVP_CIPHER_CTX` 168, `BIGNUM` 24, `ASN1_STRING` 24). No LibreSSL or OpenSSL code is used: the algorithms run on Mbed TLS 3.6.7. Failures push `ERR_PACK(library, function, reason)` codes from those headers where the entries below say so; which function code 2.6 used for each failure is not checked
- [EVP digests and HMAC](../../../core/libs/prx/libSceLibreSsl/src/EvpDigest.cpp) (`EVP_md5`, `EVP_sha256`, `EVP_sha384`, `EVP_sha512`, `EVP_MD_size`, `EVP_MD_CTX_create`/`destroy`/`init`/`cleanup`, `EVP_DigestInit_ex`, `EVP_DigestUpdate`, `EVP_DigestFinal_ex`, `EVP_Digest`, `HMAC_CTX_init`/`cleanup`, `HMAC_Init`, `HMAC_Init_ex`, `HMAC_Update`, `HMAC_Final`, `HMAC`) - `EVP_MD` objects are static tables of this library (type, size and block size); fields a title reads directly from them do not match LibreSSL's `env_md_st`. `EVP_MD_CTX.digest` holds the `EVP_MD` and `md_data` a host Mbed TLS context, which `EVP_MD_CTX_cleanup`, `EVP_MD_CTX_destroy` and `HMAC_CTX_cleanup` free; a context that is never cleaned up leaks it, as in LibreSSL. `EVP_DigestInit_ex` with a null type restarts the digest already set, and with none set pushes `EVP_R_NO_DIGEST_SET` (`ERR_PACK(ERR_LIB_EVP, EVP_F_EVP_DIGESTINIT_EX, ...)`, header values) and returns 0; whether 2.6 pushed exactly this is not checked. `HMAC_CTX` keeps the digest in `md`, the key in `key`/`key_length` (a key longer than the digest's block is stored hashed, which gives the same MAC) and the Mbed TLS context in `md_ctx.md_data`; `i_ctx` and `o_ctx` stay zero. `HMAC_Init_ex` reuses the stored key or digest when the argument is null, as the manual says; with neither a digest given nor one set it throws. `HMAC_Init` with a key and a digest clears the context first (the manual: it initializes the context), otherwise it is `HMAC_Init_ex`. `HMAC` with a null output uses a static buffer. A non-null `ENGINE` argument throws, as no engine is ever handed out. Using a context before it was set up throws instead of crashing
- [EVP ciphers](../../../core/libs/prx/libSceLibreSsl/src/EvpCipher.cpp) (`EVP_aes_{128,192,256}_{cbc,cfb8,ctr,gcm}`, `EVP_CIPHER_block_size`, `EVP_CIPHER_CTX_new`/`free`/`init`/`cleanup`/`set_padding`/`ctrl`, `EVP_CipherInit_ex`, `EVP_EncryptInit_ex`, `EVP_DecryptInit_ex` and the matching `Update`/`Final_ex` calls) - prototypes from the 2.6.3 `evp.h`, behaviour from its EVP_EncryptInit(3); the AES work runs on Mbed TLS. `EVP_CIPHER` objects are static tables of this library whose fields do not match LibreSSL's `evp_cipher_st`. The guest's `EVP_CIPHER_CTX` keeps LibreSSL's layout and the fields `cipher`, `encrypt`, `buf_len`, `oiv`, `iv` (the running CBC/CFB8 IV, the CTR counter), `buf` (partial block, the CTR keystream block), `num` (CTR keystream position), `key_len`, `flags` (`EVP_CIPH_NO_PADDING` 0x100 as `EVP_CIPHER_CTX_set_padding` sets it), `final_used`, `block_mask` and `final` (the held-back last decrypted block) hold their LibreSSL meanings; the key schedule and GCM state are a host object in `cipher_data` that `EVP_CIPHER_CTX_cleanup` and `EVP_CIPHER_CTX_free` release. Passing a cipher to an init call clears the context except `flags` and `encrypt`, a null cipher, key or IV keeps the one set before, as the manual describes, and CTR restarts its position. CBC buffers partial blocks and with padding holds back the last whole block when decrypting, so every `Update` writes at most `inl + 15` bytes (encryption) or `inl + 16` bytes (decryption); in-place calls are allowed. Failures push the 2.6 header codes the call names: `EVP_R_NO_CIPHER_SET` from `EVP_CipherInit_ex` and `EVP_CIPHER_CTX_ctrl`, `EVP_R_DATA_NOT_MULTIPLE_OF_BLOCK_LENGTH` from either `Final_ex` without padding, `EVP_R_WRONG_FINAL_BLOCK_LENGTH` and `EVP_R_BAD_DECRYPT` from `EVP_DecryptFinal_ex`, `EVP_R_CTRL_NOT_IMPLEMENTED` from a control on a cipher other than GCM, `EVP_R_INITIALIZATION_ERROR` when Mbed TLS rejects a key; which function code LibreSSL 2.6 used for each is not checked. GCM takes AAD through `Update` with a null output, IVs of any length set with `EVP_CTRL_GCM_SET_IVLEN` (default 12), `EVP_CTRL_GCM_GET_TAG` after `EVP_EncryptFinal_ex` and `EVP_CTRL_GCM_SET_TAG` (1 to 16 bytes) before `EVP_DecryptFinal_ex`, which returns 0 for a wrong or missing tag; invalid tag lengths or a tag request in the wrong direction return 0, the other GCM controls (`SET_IV_FIXED`, `IV_GEN`, ...) throw, and after a `Final_ex` the next message needs a new IV. An `Update` in the direction the context was not set up for, a negative length, null buffers, using a CBC/CFB8/CTR context without a key and a non-null `ENGINE` throw
- [CMAC_CTX_new, CMAC_CTX_free, CMAC_Init, CMAC_Update and CMAC_Final](../../../core/libs/prx/libSceLibreSsl/src/EvpCipher.cpp) - prototypes from the 2.6.3 `cmac.h`, behaviour from the current CMAC_Init(3); the MAC is Mbed TLS's AES-CMAC (RFC 4493). `CMAC_Init` accepts the three AES-CBC ciphers (others throw), returns 0 with no cipher chosen, and a key length other than the cipher's pushes `EVP_R_INVALID_KEY_LENGTH` and returns 0; with key and cipher null and length 0 it restarts the keyed context and returns 0 for one never keyed. `CMAC_Update` and `CMAC_Final` return 0 before a key is set. `CMAC_Final` with a null output only stores the length (16). An `Update` or a second `Final` after `CMAC_Final` without a new `CMAC_Init` throws, as continuing after the final block is not supported
- [AES key wrap ciphers and the libSceLibreSsl3 helpers](../../../core/libs/prx/libSceLibreSsl/src/EvpCipher.cpp) - libSceLibreSsl3 exports `EVP_aes_{128,192,256}_wrap`, `EVP_sha1`, `EVP_sha224`, `BIO_up_ref` and `ERR_peek_last_error`, and this library implements them for it through `LibreSsl*_nid_no_patch` helpers, so both modules share one object model, error queue and set of static tables. The wrap ciphers follow the LibreSSL 3.4.1 `evp.h` (`EVP_CIPHER_CTX_FLAG_WRAP_ALLOW` 0x1, `EVP_R_WRAP_MODE_NOT_ALLOWED` 170) and the current EVP_aes_128_cbc(3): an init call with one of them on a context without the flag pushes that code and returns 0. Each `Update` wraps (RFC 3394, Mbed TLS's NIST KW) or unwraps its whole input: a multiple of 8 bytes, at least 16 to wrap and 24 to unwrap, writing 8 bytes more or less; other lengths and a failed integrity check return 0, `Final_ex` writes nothing. Only the RFC 3394 default IV is supported (another IV throws), and a null output (a size query in some OpenSSL versions) throws
- [ERR_get_error, ERR_peek_error, ERR_clear_error, ERR_remove_thread_state and ERR_free_strings](../../../core/libs/prx/libSceLibreSsl/src/Error.cpp) - prototypes from the 2.6.3 `err.h`, behaviour from ERR_get_error(3), ERR_clear_error(3), ERR_remove_state(3) and ERR_load_crypto_strings(3). Each thread has its own queue of `ERR_PACK(library, function, reason)` codes (returned as the guest's 64-bit `unsigned long`), holding the last `ERR_NUM_ERRORS` (16) codes. Only the failures listed in the other entries push codes; others return their failure value with the queue unchanged, where LibreSSL may push one. `ERR_remove_thread_state` with a null id empties the calling thread's queue; another thread's id throws, as `CRYPTO_THREADID` values are not mapped to threads. No error strings are registered, so `ERR_free_strings` has nothing to free; `ERR_error_string` and `ERR_error_string_n` stay unimplemented, as the library, function and reason names and the numeric form LibreSSL prints for codes without a name are not documented
- [OPENSSL_add_all_algorithms_noconf, EVP_cleanup, SSL_library_init, SSL_load_error_strings, OBJ_cleanup, CONF_modules_free, OPENSSL_load_builtin_modules, CRYPTO_cleanup_all_ex_data, CRYPTO_num_locks, CRYPTO_set_locking_callback, CRYPTO_set_add_lock_callback](../../../core/libs/prx/libSceLibreSsl/src/Library.cpp) - prototypes from the 2.6.3 `evp.h`, `ssl.h`, `objects.h`, `conf.h` and `crypto.h`. Their only effect in LibreSSL is on state this library does not have: the digest and cipher name tables (the current OpenSSL_add_all_algorithms(3): static in LibreSSL; `EVP_cleanup` has no effect), error strings (none are registered), objects added with `OBJ_create`, loaded configuration modules and ex_data (the current CRYPTO_set_ex_data(3): `CRYPTO_cleanup_all_ex_data` has no effect), none of which an export of this build creates, so they return without changing anything; `SSL_library_init` returns 1 as SSL_library_init(3) says. `CRYPTO_num_locks` returns `CRYPTO_NUM_LOCKS`, 41 in the 2.6.3 `crypto.h` and the current CRYPTO_lock(3). The library locks internally, so the callbacks given to `CRYPTO_set_locking_callback` and `CRYPTO_set_add_lock_callback` are stored and never called; whether 2.6 called them is not checked
- [ENGINE_by_id, ENGINE_cleanup, ENGINE_ctrl_cmd, ENGINE_finish, ENGINE_free, ENGINE_get_id, ENGINE_init, ENGINE_load_builtin_engines, ENGINE_load_private_key and ENGINE_set_default](../../../core/libs/prx/libSceLibreSsl/src/Library.cpp) - prototypes from the 2.6.3 `engine.h`; behaviour from the current ENGINE_new(3), which documents LibreSSL without ENGINE support: the arguments are ignored, `ENGINE_by_id` and `ENGINE_load_private_key` return null, `ENGINE_init`, `ENGINE_finish`, `ENGINE_free`, `ENGINE_ctrl_cmd` and `ENGINE_set_default` return 0 and `ENGINE_get_id` returns an empty string. LibreSSL 2.6 still had engines; which built-in engines the console's module offers is unknown. `ENGINE_get_first`, `ENGINE_get_next` and `ENGINE_ctrl`, which that manual does not cover, stay unimplemented
- [BIO_s_mem, BIO_s_file, BIO_new, BIO_new_mem_buf, BIO_new_fp, BIO_free, BIO_write, BIO_puts, BIO_printf and BIO_ctrl](../../../core/libs/prx/libSceLibreSsl/src/Bio.cpp) - prototypes from the 2.6.3 `bio.h` and `buffer.h`, behaviour from BIO_new(3), BIO_s_mem(3), BIO_s_file(3), BIO_ctrl(3), BIO_read(3) and BIO_printf(3) of that tree. `BIO` and `BIO_METHOD` are host objects, so the fields of LibreSSL's public `bio_st` and `bio_method_st` cannot be read from them (2.6 reads them only through functions this module does not export). Only memory and file BIOs exist; `BIO_new` with another method throws. A memory BIO keeps its data in a `BUF_MEM` (the 2.6 layout, guest heap) that `BIO_get_mem_ptr` hands out and `BIO_free` frees only with `BIO_CLOSE`; `BIO_new_mem_buf` (length -1: `strlen`) is read only, refuses writes with -1 and `BIO_R_WRITE_TO_READ_ONLY_BIO` and is rewound by `BIO_reset`. File BIOs wrap the guest's `FILE` through libc (`fopen`, `fwrite`, `fseek`, `ftell`, `feof`, `fflush`, `fclose`), so names are guest paths; `BIO_read_filename` and its siblings open with `rb`, `wb`, `ab`, `a+b` or `r+b` (the console's stdio does not translate line ends) and return 0 with `BIO_R_NO_SUCH_FILE` when `fopen` fails, `BIO_reset` and `BIO_seek` return 0 or -1 and `BIO_tell` the position. Controls a BIO does not handle return 0, as BIO_ctrl(3) says for source/sink BIOs; `BIO_set_mem_buf` throws, as no `BUF_MEM` constructor is exported. `BIO_printf` formats with the guest libc's `vsnprintf` and returns the byte count or -1. `BIO_free` returns 0 for a null BIO and otherwise drops one reference. Null BIOs, null data with a length, negative lengths, writes to a file BIO without a stream and `BIO_new_mem_buf` with a null buffer or a length below -1 throw. `BIO_read` and `BIO_gets` are not exported by the console's module
