# libSceUlt technical debt

### Unknown function info

- [Bound condition variables](../../../core/libs/prx/libSceUlt/Export.cpp) use the creation-time mutex, inferred from PPSA28061 callers of `_sceUltConditionVariableCreate`; the wait caller reloads only the condition argument. Error precedence, busy/state errors, FIFO signal selection and unsupported recursive waits have not been measured on PS5 hardware. Non-null options and waits at recursion depth above one throw. A live condition prevents destroying its bound mutex. Finalization follows the existing host mutex lifecycle: it invalidates conditions and wakes queued or reacquiring waiters with a state error. Scheduling priority and build-version validation are not implemented.

- [libSceUlt ulthreads](../../../core/libs/prx/libSceUlt/Export.cpp) - `_sceUltUlthreadRuntimeOptParamInitialize`, `_sceUltUlthreadRuntimeCreate` and `_sceUltUlthreadCreate` are assumed to take the same arguments as the existing exports without the underscore, including the trailing build version. `sceUltUlthreadTryJoin` is assumed to return `ULT_ERROR_BUSY` while the ulthread runs, and `sceUltUlthreadRuntimeDestroy` to return `ULT_ERROR_BUSY` while an ulthread created on the runtime is not joined. Neither error has been confirmed on PS5 hardware
- [libSceUlt queues](../../../core/libs/prx/libSceUlt/Export.cpp) - the added `sceUltQueuePop`, `sceUltQueueTryPush`, `sceUltQueueDestroy` and `sceUltQueueDataResourcePoolDestroy` signatures are inferred from the existing push/pop and object APIs. Queue destruction is assumed to reject blocked callers with `ULT_ERROR_BUSY` and otherwise discard queued data; pool exhaustion returns `ULT_ERROR_AGAIN`. These rules, alignment checks and shared slot limits have not been confirmed on PS5 hardware or a title.
- [sceUltQueueCreate, sceUltQueueDataResourcePoolCreate](../../../core/libs/prx/libSceUlt/Export.cpp) - a non-null option parameter is accepted and ignored, as the other Ult create calls already do. [OpenOrbis](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/00d087b2323bf377fd39b7163a256977383cb232/include/orbis/Ult.h) declares `sceUltQueueOptParamInitialize` and `sceUltQueueDataResourcePoolOptParamInitialize` without their structures; the PS Vita libult in [RPCS3](https://github.com/RPCS3/rpcs3/blob/13aa88c3c4d66ea8799e987f7d762d90943ab17b/rpcs3/Emu/PSP2/Modules/sceUlt.h#L25-L78) defines both as a 16-byte reserved header followed by reserved fields, 128 bytes, with no settings, and [fpPS4](https://github.com/red-prig/fpPS4/blob/5ffbdbbd76b4da6e4b8721743ea491f494b28913/src/ps4_libsceult.pas#L142-L172) keeps them as 128 opaque bytes. That the PS5 structures carry no settings either is assumed from these, not verified
- [_sceUltWaitingQueueResourcePoolCreate, _sceUltSemaphoreCreate, _sceUltMutexOptParamInitialize, _sceUltMutexCreate, _sceUltQueueDataResourcePoolCreate and _sceUltQueueCreate](../../../core/libs/prx/libSceUlt/Export.cpp) (libSceUlt) forward to the exports without the underscore; that their argument lists match is inferred from the other underscore Ult exports, not measured
- [sceUltGetConditionVariableInfo, sceUltGetMutexInfo, sceUltGetQueueDataResourcePoolInfo, sceUltGetQueueInfo, sceUltGetReaderWriterLockInfo, sceUltGetSemaphoreInfo, sceUltGetUlthreadInfo, sceUltGetUlthreadRuntimeInfo, sceUltGetWaitingQueueResourcePoolInfo, sceUltAbstractThreadFactoryCreateThread, sceUltAbstractThreadFactoryGetNumMaxThreads, sceUltAbstractThreadFactoryJoinThread, sceUltKernelThreadFactoryFinalize, sceUltKernelThreadFactoryGetFactoryPointer, sceUltKernelThreadFactoryInitialize, sceUltModuleFinalize, sceUltModuleInitialize, sceUltUlthreadFactoryFinalize, sceUltUlthreadFactoryGetFactoryPointer, sceUltUlthreadFactoryGetWorkAreaSize, sceUltUlthreadFactoryInitialize](../../../core/libs/prx/libSceUlt/Export.cpp) (libSceUlt) - throwing stubs declared without parameters from the firmware export database (aerolib.csv): [OpenOrbis](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/0a1aaf9dd4a92695538bdeb09fb056d06dd11725/include/orbis/Ult.h) lists the info calls by name only, [SharpEmu](https://github.com/sharpemu/sharpemu/blob/5052fae0718ee17eb4c7fae0a52b472738c64aaa/src/SharpEmu.Libs/Ult) implements none of them, and no source names the factory or module calls; their guest signatures are unverified on hardware
- [sceUltMutexTryLock](../../../core/libs/prx/libSceUlt/Export.cpp) (libSceUlt) - the `(mutex)` signature and `ULT_ERROR_BUSY` for a mutex another thread holds follow [SharpEmu](https://github.com/sharpemu/sharpemu/blob/5052fae0718ee17eb4c7fae0a52b472738c64aaa/src/SharpEmu.Libs/Ult/UltExports.Sync.cs#L272-L296). SharpEmu refuses a mutex the caller already holds with `0x80810005`; here the caller's own mutex is taken again and counted, as `sceUltMutexLock` already does, so it needs one unlock per successful try. Neither answer is measured on a PS5
- [sceUltConditionVariableSignalAll](../../../core/libs/prx/libSceUlt/Export.cpp) (libSceUlt) - the `(condition)` signature follows [SharpEmu](https://github.com/sharpemu/sharpemu/blob/5052fae0718ee17eb4c7fae0a52b472738c64aaa/src/SharpEmu.Libs/Ult/UltExports.Sync.cs#L428-L470); it wakes every queued waiter of the bound condition, with the same null, unknown-object and finalized-state errors as `sceUltConditionVariableSignal`. [sceUltConditionVariableCreate](../../../core/libs/prx/libSceUlt/Export.cpp) forwards to `_sceUltConditionVariableCreate`; that it takes the same arguments is inferred from the other underscore pairs, as for the creates above
- [sceUltUlthreadGetSelf, sceUltUlthreadExit, sceUltUlthreadYield](../../../core/libs/prx/libSceUlt/Export.cpp) (libSceUlt) - the `(ulthread** out)`, `(int32_t status)` and `()` signatures follow [SharpEmu](https://github.com/sharpemu/sharpemu/blob/5052fae0718ee17eb4c7fae0a52b472738c64aaa/src/SharpEmu.Libs/Ult/UltExports.cs#L364-L417), as does `0x80810005` (SharpEmu's `ErrorPermission`, `ULT_ERROR_PERMISSION` here) from `GetSelf` and `Exit` on a thread that is not an ulthread; `GetSelf` checks the null output first. `Exit` ends the ulthread's host thread through `scePthreadExit`, which skips the frames above it without unwinding them, and `Join` then reports the status. `Yield` yields the host thread, as SharpEmu does on any thread, because each ulthread runs on its own host thread here rather than on a worker of the runtime
- [sceUltSemaphoreOptParamInitialize, sceUltQueueOptParamInitialize, sceUltQueueDataResourcePoolOptParamInitialize, sceUltWaitingQueueResourcePoolOptParamInitialize, sceUltUlthreadOptParamInitialize and sceUltReaderWriterLockOptParamInitialize](../../../core/libs/prx/libSceUlt/Export.cpp) (libSceUlt) zero 128 bytes, the size of the PS Vita libult option structures in [RPCS3](https://github.com/RPCS3/rpcs3/blob/13aa88c3c4d66ea8799e987f7d762d90943ab17b/rpcs3/Emu/PSP2/Modules/sceUlt.h#L25-L78) and the size [SharpEmu](https://github.com/sharpemu/sharpemu/blob/5052fae0718ee17eb4c7fae0a52b472738c64aaa/src/SharpEmu.Libs/Ult/UltExports.cs#L109-L152) gives the ulthread and runtime option parameters. [sceUltConditionVariableOptParamInitialize](../../../core/libs/prx/libSceUlt/Export.cpp) only rejects a null parameter, like SharpEmu's [underscore forms](https://github.com/sharpemu/sharpemu/blob/5052fae0718ee17eb4c7fae0a52b472738c64aaa/src/SharpEmu.Libs/Ult/UltExports.Sync.cs#L95-L125): its size is unknown, so nothing is written. The creates here ignore these options (`_sceUltConditionVariableCreate` throws for any non-null one). That the PS5 structures match, their contents and the build version argument are unverified
- [The reader-writer lock](../../../core/libs/prx/libSceUlt/src/ReaderWriterLock.cpp) (libSceUlt) - the signatures follow the PS Vita libult in [RPCS3](https://github.com/RPCS3/rpcs3/blob/13aa88c3c4d66ea8799e987f7d762d90943ab17b/rpcs3/Emu/PSP2/Modules/sceUlt.cpp) (a 256-byte lock and 128-byte option structures), not a PS5 binary. The rules are assumed: readers may take the lock while a writer waits, a thread that holds the write lock gets `ULT_ERROR_STATE` for any further lock instead of waiting on itself, a reader asking for the write lock waits on its own read lock, and the try forms return `ULT_ERROR_BUSY`.
### Functional

- [libSceUlt queues](../../../core/libs/prx/libSceUlt/Export.cpp) use preallocated host storage instead of the supplied guest work area; its existing size formula and the 512-byte object layouts remain unverified. Waiting-queue pool thread limits and waiter priority ordering are not implemented. Finalization wakes blocked queue callers with `ULT_ERROR_STATE`.
- [sceUltWaitingQueueResourcePoolDestroy](../../../core/libs/prx/libSceUlt/Export.cpp) refuses with `ULT_ERROR_BUSY` only when a thread is currently waiting on a pool-backed mutex, semaphore or queue, matching the PS5 libSceUlt disassembly (0x473a in or55417wcDk); bound but idle objects do not block pool destruction. Waiting-queue pool guest work area node accounting is not implemented.
- [sceUltMutexDestroy](../../../core/libs/prx/libSceUlt/Export.cpp) returns `ULT_ERROR_BUSY` when the mutex is held or has waiting threads, tracked via owner and waiter counts in `UltMutexState`. Prosper (`hle_ult.cpp`) logs a destroy of a held mutex and returns `ULT_OK`; AnyPS5 returns `ULT_ERROR_BUSY` to prevent destroying active mutexes.

- The following pending declarations have unverified signatures and behavior; they are parameterless import-resolution declarations and throw through `NotImplemented_nid_no_patch`: [`_sceUltConditionVariableOptParamInitialize`](../../../core/libs/prx/libSceUlt/Export.cpp).
