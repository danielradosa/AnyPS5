# libSceCompanionHttpd technical debt

### Unknown function info

- [sceCompanionHttpdOptParamInitialize, sceCompanionHttpdInitialize](../../../core/libs/prx/libSceCompanionHttpd/Export.cpp) (libSceCompanionHttpd) - the option block is taken as 0x60 bytes: titles fill a work memory pointer at +0x08, its size at +0x10 and a temporary data mount point at +0x58 after `sceCompanionHttpdOptParamInitialize`. Its other fields and the defaults the console writes are unknown, so `sceCompanionHttpdOptParamInitialize` zeroes the 0x60 bytes and `sceCompanionHttpdInitialize` reads none of them; both reject a null block with `INVALID_PARAM`
- [sceCompanionHttpdAddHeader, sceCompanionHttpdSetBody and sceCompanionHttpdGet2ndScreenStatus](../../../core/libs/prx/libSceCompanionHttpd/Export.cpp) (libSceCompanionHttpd) - the prototypes are known from orbital and shadPS4 (`(const char* key, const char* value, SceCompanionHttpdResponse*)`, `(const char* body, size_t bodySize, SceCompanionHttpdResponse*)` and `(SceUserServiceUserId userId)`), but they still throw: whether the header node and the body are copied into library memory or referenced, and who frees them, is unknown, and so is what the second screen status call returns for a user without a connected device (a status value or `NOT_CONNECTED`)
- [sceCompanionHttpdInitialize2, Terminate, Start, Stop, GetEvent, GetUserId, RegisterRequestCallback, RegisterRequestCallback2, RegisterRequestBodyReceptionCallback, UnregisterRequestCallback, UnregisterRequestBodyReceptionCallback and SetStatus](../../../core/libs/prx/libSceCompanionHttpd/Export.cpp) (libSceCompanionHttpd) - nothing is measured on a console; which code each call returns, and the order of the checks, follow the code names. The PS4 prototypes are in [orbital](https://github.com/AlexAltea/orbital/blob/cc408367da6a6ebbf5ac1ac559fefeadc73b2831/tools/ida/db_types.json); the callback types, the 32-byte response (status, header list, body, body size) and the error codes come from [shadPS4](https://github.com/shadps4-emu/shadPS4/blob/23c41333822fe8eca4c609b43119180af63ae4ac/src/core/libraries/companion/companion_httpd.h), which only stubs the calls:
  - No server is opened and no second-screen device can connect, so `sceCompanionHttpdGetEvent` always answers `NO_EVENT` (0x80E40008), as shadPS4 does (shadPS4 also writes a disconnect event into the output; this does not), `sceCompanionHttpdGetUserId` answers `USER_NOT_FOUND` (0x80E4000E) for every address, and the registered callbacks are never called.
  - `sceCompanionHttpdInitialize2` does not read its option parameter, whose layout is unknown, and accepts a null one; it shares one initialized state with `sceCompanionHttpdInitialize`, and a second initialization through either returns `ALREADY_INITIALIZED` (0x80E40007). Every other call except `sceCompanionHttpdSetStatus` returns `NOT_INITIALIZED` (0x80E40006) before it and after `sceCompanionHttpdTerminate`. `sceCompanionHttpdStart` and `sceCompanionHttpdStop` return `ALREADY_STARTED` (0x80E4000A) and `NOT_STARTED` (0x80E4000B); `sceCompanionHttpdTerminate` also stops a started server and drops both callbacks, whether the console refuses to terminate a started server is unknown.
  - A null output or callback returns `INVALID_PARAM` (0x80E40004). The two request-callback registrations share one slot, as there is one `sceCompanionHttpdUnregisterRequestCallback`; the body-reception callback has its own. Registering into an occupied slot returns `ALREADY_REGISTERED`, taken as 0x80E4000C (between `NOT_STARTED` and `NOT_CONNECTED`; shadPS4's header has 0x80E4000, one digit short). Unregistering an empty slot succeeds.
  - `sceCompanionHttpdSetStatus` writes the status into the title's response and returns 0 without an initialization check; it touches nothing else
