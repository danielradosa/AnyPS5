They act on the connections of PR #5226 (below) and follow its conventions: an unknown connection, or one whose context was terminated, throws. The signatures follow [SharpProspero](https://github.com/SvenGDK/SharpProspero/blob/5dfdb4b0b166e83dc9ae275001afb695f12c7174/src/SharpProspero/Interop/Net/Http.cs): `(int connection)`, `(int connection, uint32 option)` twice, `(int connection, SceSslVersion version)`, `(int connection, const char* protocols)` with the protocols in ALPN wire form (each name preceded by its length byte) and `const uint8* (int connection)`. None was measured on a PS5.
  - The enable and disable calls record which verification bits the title turned on and off (the last call wins for a bit), without assuming the library's default set, which is unknown; any bit is accepted. `sceSslSetMinSslVersion` stores a version from 0 (the library's own floor) to 5 (TLS 1.2), SharpProspero's `SceSslVersion` range, and returns `INVALID_VALUE` (0x8095F007, the value error the console returns from `sceSslGetMemoryPoolStats`) for any other value. `sceSslSetAlpn` stores a well-formed, non-empty wire-form list of at most 0xFFFF bytes and returns `INVALID_VALUE` for a null, empty or truncated one. These settings would steer a handshake; with no TLS transport they only appear in the error `sceSslConnect`, `sceSslRead` and `sceSslWrite` throw, so a later implementation can see what the title asked for.
  - No handshake ever completes, so `sceSslGetAlpnSelected` returns null, the "nothing negotiated" answer. `sceSslClose` marks the connection closed and returns 0, also when called again or before `sceSslConnect`, since no secure channel exists to send a close notification on; afterwards the three transport calls throw that the connection was closed. The console's errors for these states are unknown

- [libSceSsl](../../../core/libs/prx/libSceSsl/Export.cpp) - libSceSsl certificate/context support uses source-built Mbed TLS 3.6.7 (068ff080b369adfac81509f9b57b2afabaf82dc5), selected under its offered GPL-2.0-or-later license, compatible with AnyPS5's GPLv2 license. It parses DER and PEM certificate chains, validates unencrypted private keys and matches client public/private keys. Loading certificates does not authenticate a TLS peer, validate a remote hostname, or require the client identity to chain to the server CA store; those decisions belong to a future handshake implementation. HTTP remains offline. No proprietary root bundle is included and the host trust store is not imported. Only explicitly loaded authorities appear in CA enumeration. Context-aware reader prototypes are corroborated by orbital commit cc408367da6a6ebbf5ac1ac559fefeadc73b2831's tools/ida/db_types.json and SharpProspero 5dfdb4b0b166e83dc9ae275001afb695f12c7174 Interop/Net/Http.cs; LoadCert and the 0x20 pool-stats/0x10 CA-list layout follow the latter. These are public compatibility references, not PS5 hardware evidence. sceSslGetNameEntryInfo currently emits numeric dotted OIDs and raw ASN.1 string-value octets; the OID is terminated, an extra value terminator is written only if capacity permits, and reported value length excludes that terminator. sceSslGetSerialNumber emits DER INTEGER content octets including leading sign padding, without INTEGER tag/length. Null data buffers support length queries. The exact Sony name/serial formatting, small-buffer length conventions, return codes and whether loading replaces/appends authorities still require hardware confirmation; the implementation appends authorities and replaces a supplied client identity atomically. Unknown error cases throw typed exceptions instead of inventing console error codes; the existing invalid-argument and no-authority constants are retained for established paths. The configured pool size limits requested bytes for real Mbed TLS allocations and returned CA/name data storage, recording current and peak requested bytes. Native allocator headers, Context/CertificateChain/Identity wrappers, registry maps/vectors/shared_ptr control blocks, temporary OID strings and opaque-handle tombstones are host bookkeeping outside this budget; repeated load/free can grow that bookkeeping until Term. No console-exact allocator overhead or up-front reservation is claimed. All exported operations serialize through the library mutex, and the privately linked backend uses the context active on that thread for allocations. Allocation failure or invalid CA/client/key input rolls back newly allocated backend state without replacing prior data. Faults in C++ bookkeeping allocation were structurally reviewed, not runtime fault-injected. CA handle-list snapshots retain their certificates over UnloadCert; DER byte snapshots and name handles are independent copies. Freeing the last retaining list after unload expires its certificate handles. Name/certificate tokens are not reused within a context, preventing stale pointers from resolving to a later object there. Term releases snapshots, copied names, keys and certificates; all associated pointers expire. These ownership choices and post-unload snapshot lifetimes are emulation semantics pending hardware confirmation. Foreign, freed and cross-context CA lists, names and certificates are rejected, except by `sceSslFreeCaCerts`, which clears a foreign list without an error (see below). Validation uses self-generated P-256 root/client fixtures and a matching/mismatching private key, not a retail executable or console dump. Tests cover DER roundtrip, PEM chains including partial parse rejection, multi-valued names, serial sign padding, eight-argument guest ABI, caller-buffer canaries, failed import rollback, pool exhaustion/peak/release, unload snapshots, stale/cross-context ownership and four concurrent contexts. The baseline shared library fails the real pool-stats regression with sceSslGetMemoryPoolStats not implemented; the candidate backend-linked suite passes. Open PR #1119 by TideOPL overlaps pool stats but models zero allocations; its idea is acknowledged and this batch measures real backend/data allocations. Mbed TLS's optional Everest accelerator files are Apache-2.0-only. This build explicitly disables MBEDTLS_ECDH_VARIANT_EVEREST_ENABLED and removes the unused everest target from mbedcrypto link dependencies. The linked library/include/p256-m sources were checked for the offered Apache-2.0 OR GPL-2.0-or-later license; the GPL option is selected. The unmodified dependency tree retains every upstream license notice.

- [sceSslCreateConnection, sceSslDeleteConnection, sceSslSetVerifyCallback, sceSslConnect, sceSslRead, sceSslWrite](../../../core/libs/prx/libSceSsl/Export.cpp) (libSceSsl) - imported by `ffmpeg.prx`. Signatures follow [SharpProspero](https://github.com/SvenGDK/SharpProspero/blob/60977b29103452b9681ae10c7a9011d44965bf16/src/SharpProspero/Interop/Net/Http.cs#L195-L252), which also says the socket stays open after `sceSslDeleteConnection` and that `sceSslRead` returns 0 at the end of the stream. An unknown context returns `SSL_ERROR_INVALID_ID` (0x8095F006), as `sceSslGetMemoryPoolStats` does on the console and as [KytyPS5](https://github.com/KytyPS5/KytyPS5/blob/4865dd92ca6b6bb907748f125883093af038f53b/src/libs/network.cpp#L2688-L2720) and [sharpemu](https://github.com/sharpemu/sharpemu/blob/29021b5a71bbc80f262d887e6ba18b3a72963f49/src/SharpEmu.Libs/Network/SslExports.cs#L41-L54) return for other context calls; for an unknown connection, a connection whose context was terminated and a null host the console's codes are unknown, so these throw. `sceSslConnect` runs a TLS 1.2 client handshake with Mbed TLS 3.6.7 over the host socket that the guest number maps to in the libkernel or libSceNet socket table, and `sceSslRead` and `sceSslWrite` carry application data over it. TLS 1.3 is compiled out: SharpProspero's `SceSslVersion` ends at TLS 1.2, and Mbed TLS 1.3 needs PSA crypto state that is process-wide rather than allocated from a context's pool. Connection state is allocated from the context's pool and returned to it by `sceSslDeleteConnection`; a connection keeps the pool alive after `sceSslTerm`. The server's chain is checked against the CAs loaded with `sceSslLoadCert`, its validity dates and the host name the connection was created with, which is also sent as SNI, and `sceSslConnect` returns the first failure the connection's verify options select (the verify option entry below lists the bits and codes); no root bundle is shipped and the console's built-in roots are unknown, so with no CA loaded a connection with the initial options returns `SSL_ERROR_UNKNOWN_CA` (0x8095F00C). A client certificate loaded with `sceSslLoadCert` is sent when the server asks for one. The result of the first completed `sceSslConnect` is final for the connection: a failure sends close_notify, later `sceSslConnect` calls return the same code, and `sceSslRead` and `sceSslWrite` throw. With a verify callback set it is called once after the handshake, outside the connection's lock, with the connection id, that code (0 when the chain passed), handles to a copy of the peer chain that the certificate readers of the connection's context accept until the connection is deleted (the handles stay registered in the context until it is terminated), the chain length and the user argument; a negative return fails the connect with `SSL_ERROR_APPLICATION_VERIFICATION_CALLBACK_CHECK` (0x8095F0FD) and any other return accepts the connection whatever the code was, following SharpProspero's "a negative return fails the handshake" ([https://github.com/SvenGDK/SharpProspero/blob/60977b29103452b9681ae10c7a9011d44965bf16/src/SharpProspero/Interop/Net/Http.cs#L195-L252](https://github.com/SvenGDK/SharpProspero/blob/60977b29103452b9681ae10c7a9011d44965bf16/src/SharpProspero/Interop/Net/Http.cs#L195-L252)). Whether the id is the context or the connection, whether the second argument is that code or the bits of the failed checks, the chain element type, when the console runs the callback and whether a non-negative return overrides a failed check are unknown. A `sceSslConnect` from inside the callback, or from another thread while it runs, throws. A non-blocking socket that would block returns `SSL_ERROR_WANT_POLLIN` (0x8095F013) or `SSL_ERROR_WANT_POLLOUT` (0x8095F014) from `sceSslConnect`, `sceSslRead` and `sceSslWrite`; the next `sceSslConnect` resumes the handshake, and `sceSslWrite` returns the part it sent before blocking. A blocking libSceNet socket whose `SO_RCVTIMEO` expires returns `SSL_ERROR_READ_TIMEOUT` (0x80951710) from `sceSslConnect` and `sceSslRead`, and the call can be repeated; one whose `SO_SNDTIMEO` expires throws, as no write timeout code is known. libkernel keeps its timeouts above the host socket, so they do not bound SSL reads and writes on a libkernel socket. A reset (`ECONNRESET`, `EPIPE`, `WSAECONNRESET`, `WSAECONNABORTED`, `WSAENETRESET`) returns `SSL_ERROR_SOCKET_CLOSED` (0x8095170D), as does a transport that ends without close_notify during the handshake, and a fatal alert returns `SSL_ERROR_FATAL_ALERT` (0x8095F010); when one of these ends the handshake the session is dropped and the next `sceSslConnect` starts over. Which situation returns which code is inferred: [KytyPS5](https://github.com/KytyPS5/KytyPS5/blob/4865dd92ca6b6bb907748f125883093af038f53b/src/libs/errno.h#L512-L546) gives the names and values but not when the console returns them, so `WANT_POLLIN` and `WANT_POLLOUT` rather than `SSL_ERROR_EAGAIN` (0x8095F00F) for a socket that would block, `SOCKET_CLOSED` rather than `SSL_ERROR_EOF` (0x8095177C) for a handshake cut short, `READ_TIMEOUT` for an expired receive timeout, `FATAL_ALERT` for a fatal alert, `INVALID_CERT` (0x8095F00A) for a verification failure no option names, and a repeated `sceSslConnect` returning the first result, 0 included, rather than an error are all unverified on a console. Other handshake and socket failures, a read or write before the handshake, after a failed verification or after `sceSslClose`, a descriptor that is not a socket, a null buffer, write flags other than 0 and read flags other than 0 and `MsgFlagPartialRead` (1) throw, as their console codes are unknown; `MsgFlagPeek` (3) is not implemented. `sceSslRead` returns what one Mbed TLS read delivers, up to `len`, with flags 0 and with `MsgFlagPartialRead` alike; SharpProspero describes `sceSslRead` as reading up to `len` but `MsgFlagPartialRead` as returning before the buffer is full, so whether flags 0 waits to fill the buffer is unknown. It returns 0 after the server's close_notify and also when the transport ends without one, as Mbed TLS reports both as the end of the stream. `sceSslWrite` sends all of `len`, capped at `INT_MAX`, and returns the count. A connection serializes its reads and writes, so a read blocked in one thread holds back a write on the same connection from another. `sceSslDeleteConnection` sends no close_notify. The socket is not checked when the connection is created, `sceSslTerm` leaves the context's connections to `sceSslDeleteConnection`, and `sceSslSetVerifyCallback` accepts any callback, null included, and returns 0. None of this is verified on the console. `SSL_ERROR_BEFORE_INIT` (0x8095F001) is never returned, as the library keeps no state apart from its contexts
