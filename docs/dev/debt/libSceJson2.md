# libSceJson2 technical debt

### Unknown function info

- [sce::Json::Parser::parse with a read callback](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - the callback's contract is taken from PPSA04540's: it returns 0 with the next character, and at the end of its data writes `'\0'` and returns -1. Characters are read until the callback returns non-zero or gives `'\0'`, and the text read is then parsed as by the `(text, size)` overload, so trailing characters after the value are rejected as there. Whether the console stops reading at the end of the top-level value, and what it returns when the callback fails before the end, are unknown
- [sce::Json::MemAllocator::notifyError](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - the PS5 mangled export identifies the error code, 64-bit size and user-data arguments. The void return and default stdout error notification follow the related [VitaSDK JSON API](https://docs.vitasdk.org/group__SceLibJsonUser.html). Its PS5 return contract and exact diagnostic wording have not been verified on a console; allocator and user-data pointers remain opaque
- [sce::Json::InitParameter2, InitParameterRtti and InitParameterRtti2](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - layouts inferred, not known. `InitParameter2` is taken as the 40-byte object of [SharpEmu](https://github.com/sharpemu/sharpemu/blob/1811cef94435db7655209fb39f65ddf258b93fd6/src/SharpEmu.Libs/Json/JsonExports.cs) and [KytyPS5](https://github.com/KytyPS5/KytyPS5/blob/eda6ba37ece127ab0396378404d99182e3e8a530/src/libs/libJson2.cpp): the allocator, its user data, the file buffer size, the 32-bit special float format type at 0x18 and 12 bytes both zero, and both constructors zero all of it. `InitParameterRtti2::setAllocatorRtti` writes the allocation parameters and user data where `setAllocator` writes the allocator, as both references do; whether the console also marks the object as using RTTI allocation is unknown. `InitParameterRtti`'s constructor writes the allocation parameters, user data and file buffer size to the first 24 bytes, an order inferred from its mangled arguments. The values of `SpecialFloatFormatType` and what they select are unknown, so `setSpecialFloatFormatType` accepts only the assumed default 0, throws for any other value, and nothing reads it: `Initializer::initialize(InitParameter2)` ignores every field as `initialize(InitParameter)` does, serializing a non-finite real throws whatever the type, and whether the type lets the parser accept NaN or infinity is unknown. The setters return nothing; whether the console's return `this` is unknown
- [sce::Json::Array::iterator default constructor and postfix increment, sce::Json::Object::Pair constructor](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - signatures come from the mangled names, but three details are inferred and not checked on a console: `Array::iterator::operator++(int)` returns the previous iterator by value through a hidden return pointer, from the standard postfix form and the exported non-trivial destructor, as `begin`, `end` and `Object::find` do; a default-constructed iterator is value-initialized; and the `Pair` constructor zeroes the 8 bytes at 0x08, as the library does for every other `Pair` it creates
- [sce::Json::Value::setNullAccessCallBack, setTypeMismatchHandler, setElementAccessFailureHandler and setSpecialFloatHandler](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - the handler types come from the mangled names. They are taken as members that return 0 and keep the handler and its context on the value they are called on, because the [VitaSDK header](https://github.com/vitasdk/vita-headers/blob/master/include/psp2/json.h) of the same library declares `setNullAccessCallback` that way (with a per-value callback field) and the PS5 library also exports `Initializer::setGlobal...` forms of all four (aerolib NID list), which would duplicate static setters. Whether the console's setters are static instead, which would move every argument by one register, is not verified. The handlers stay with the value when its content changes (set, assignment, parse into it, clear); a copy-constructed value starts without them, and values reached through a handled one (children, members) do not inherit them, both unverified. A value's own null access callback is used before the global one. A type mismatch handler is called when a get accessor finds a value of another type that is not null (null values still go to the null access callbacks, and without a mismatch handler a mismatch also does, as before); it is passed the accessed value as both of its `const Value*` arguments, as the null access callback is passed the accessed value as its parent, since values here do not know their parent, and a result of another type falls back to the default value. The element access failure handler's `int` argument and its two values, and the special float handler's `FunctionType` values and `bool*` argument, are unknown, so neither is ever called: a failed `operator[]` or `getValue` on a value with an element access failure handler throws instead of returning the null value, and serializing a non-finite real under a value with a special float handler throws, naming the handler, as it does without one
- [sce::Json::Object::insert](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - returns an iterator to the inserted pair through a hidden return pointer, as the [VitaSDK header](https://github.com/vitasdk/vita-headers/blob/master/include/psp2/json.h) declares it and as `find` returns one here; whether the PS5 export returns nothing instead is not verified. A key that is already present keeps its value and the iterator points at it, as `std::map::insert` does: the console's object is a `std::map` (its `_Tree<_Tmap_traits<..., sce::Json::Value, ...>>::_Insert_nohint` instantiation is exported), but whether its `insert` overwrites is not verified. New pairs are appended, as members are kept in insertion order here rather than sorted by key
- [sce::Json::Value::operator bool](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - true for every value that is not null (a `false` boolean included), as JsonCpp's conversion does; the VitaSDK header declares it without saying what it tests, so whether it returns a boolean value's contents instead is not verified
- [sce::Json::Parser::parse](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - a null text pointer or zero size returns `JsonErrorParse` (0x80920101) without modifying the destination Value; whether the console distinguishes a null pointer from a syntax error with a separate parameter error code is unknown. A number that overflows a double (e.g. `1e309`) throws: whether the console rejects the document or stores an infinite real is unknown
- [sce::Json::Value::setTypeMismatchHandler, setElementAccessFailureHandler and setSpecialFloatHandler](../../../core/libs/prx/libSceJson2/Export.cpp) (libSceJson2) - members of `Value` that return an int, inferred from a caller that registers them on its root `Value` before parsing into it, with the handler and its context, and accepts 0 or 0x80848104 as success; they return 0. The PS Vita library's `Value::setNullAccessCallback` is such a member too ([vitasdk](https://github.com/vitasdk/vita-headers/blob/15605617cbbb23d266f88af28899fdb573e2355e/include/psp2/json.h#L638)). The handler signatures follow the mangled names. A handler applies to the `Value` it is set on and to the values that `Value` holds then, and `Parser::parse` gives the values it creates the handlers of the `Value` it parses into, since the title reads the errors its handlers record after accessing parsed members; copies, `push_back` and `Object::operator[]` do not carry them, and how the console finds the handler of an accessed value is unknown. A typed getter on a non-null value of another type calls the type mismatch handler with the requested type, the value, null and the context, and returns the value the handler returns if it has the requested type, else the getter's default; passing null as the third handler argument (the second `Value` pointer), and the order of the two `Value` pointers, remain unverified against the console. The element access failure handler is not called: a failed `operator[]` or `getValue` on a value carrying it throws, as the error code the console passes, which the title records as its error, is unknown; without one the access still reaches the null-access callback. The special float handler is not called: serializing a non-finite real throws with or without it, as the `FunctionType` values and the `bool*` output are unknown, and the title's handler returns a different replacement for each of its two types
