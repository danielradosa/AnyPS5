- [sceSaveDataGetConvertProgress](../../../core/libs/prx/libSceSaveData.native/Export.cpp) (libSceSaveData.native) - imported by PPSA16064; signature and error codes follow the [SDK 12.000 reference](https://github.com/peterpuppy/bm/blob/3f9d1ba6b896a53080460c903f5c15af8affb80d/features/ps5/document/output/psn_12/System/Save_Data/SaveData-Reference/sce-save-data-get-convert-progress.md) (`float* progress`). Save data conversion on host filesystems completes synchronously, so the progress query returns `SAVE_DATA_OK` with the last conversion's progress (`0.0f` before any conversion or when conversion fails, `1.0f` after successful conversion), `SAVE_DATA_ERROR_PARAMETER` if `progress` is null, or `SAVE_DATA_ERROR_NOT_INITIALIZED` when the library is uninitialized; intermediate asynchronous conversion progress on console is unmeasured
- [sceSaveDataCancel](../../../core/libs/prx/libSceSaveData.native/Export.cpp) (libSceSaveData.native) - imported by PPSA23126. The signature `(SceSaveDataTransactionResourceId resource)`, the transaction-resource model and the error codes follow the [SDK 12.000 reference](https://github.com/peterpuppy/bm/blob/3f9d1ba6b896a53080460c903f5c15af8affb80d/features/ps5/document/output/psn_12/System/Save_Data/SaveData-Reference/sce-save-data-cancel.md): `sceSaveDataCreateTransactionResource` hands out positive ids, at most 16 live (`RESOURCE_FULL` 0x809F001A), which `sceSaveDataTerminate` deletes at the last termination; `sceSaveDataPrepare` starts an update on a mount and `sceSaveDataCommit` or `sceSaveDataCancel` ends it. With `SCE_SAVE_DATA_PREPARE_MODE_ENABLE_CANCEL` (2) the save directory and its `.param` sidecar are copied to `_sd_txn/<resource>` beside the save root, and the cancel swaps the copy back in by renaming the updated directory aside, so files and parameters written during the update are discarded. A rename the host refuses as access denied or busy (a file in the save still open) returns `BUSY`, as the reference describes for open files; where the host allows the rename with files open (Linux and macOS, and Windows may for the delete-sharing handles guest files are opened with) those files keep writing to the discarded copy, which is removed as far as the host allows. Prepare returns `PARAMETER` for a null argument, a mode outside 2 and 4, or 4 without 2; `RESOURCE_INVALID` for a resource that was not created; `NOT_MOUNTED`; `BAD_MOUNTED` for a read-only mount; `BUSY` when the save already has an update; and `RESOURCE_BUSY` when the resource is in another update. Commit and cancel return `RESOURCE_INVALID` when the resource has no update (cancel also when it was started without mode 2), and deleting a resource in an update returns `RESOURCE_BUSY`. Not modelled: the order of these checks on the console, the debug mode 4 (all saves here are host saves, which the reference says are committed instead of cancelled, but the emulator restores them so that titles see the console behaviour), the commit's update of the modification time, what unmounting or deleting a save during an update does (the update stays open and a later cancel restores the directory), and `SCE_USER_SERVICE_ERROR_NOT_INITIALIZED`. Commit and resource creation used to succeed for any argument
- [sceSaveDataDirNameSearch](../../../core/libs/prx/libSceSaveData.native/Export.cpp) (libSceSaveData.native) - the sort keys (0 directory name, 1 user parameter, 2 blocks, 3 modification time, 5 free blocks) and orders (0 ascending, 1 descending) follow shadPS4, not a hardware run; saves with equal keys keep directory-name order before a descending reverse. Every native save reports `SAVE_DATA_BLOCKS_MAX` blocks, as `sceSaveDataGetMountInfo` does, so the two block keys keep directory-name order. The search infos (blocks, free blocks and 32 reserved bytes per returned name, following shadPS4's `OrbisSaveDataSearchInfo`) report `SAVE_DATA_BLOCKS_MAX` for both. Keys other than 0, 1, 2, 3 and 5 (including 4) and orders above 1 return `SCE_SAVE_DATA_ERROR_PARAMETER`; shadPS4 and KytyPS5 only reject keys above 5, so key 4 is rejected here because no source names it. In the directory name pattern `%` matches any run of characters, none included, and `_` exactly one, as the comments of shadPS4's matcher describe; also not confirmed on hardware
- [sceSaveDataInitialize3](../../../core/libs/prx/libSceSaveData.native/Export.cpp) (libSceSaveData.native) - a repeated initialize succeeds: PPSA12544's executable and its Unity SaveData plugin both initialize, and the plugin fails on any error. Initializations are counted and `sceSaveDataTerminate` ends the session at the last one; how the console pairs them is unknown
